**Citation**: Shuai Bai, Yuxuan Cai, Ruizhe Chen, et al. (Qwen Team, 64 authors). arXiv preprint, Nov 2025 (v1 26 Nov, v2 27 Nov 2025). arXiv:2511.21631. https://arxiv.org/abs/2511.21631. Sources read: the PDF of v2 (https://arxiv.org/pdf/2511.21631v2): §1-2, §3.2.4-3.2.5 (p. 7), §4 (pp. 9-11), §5.5 and §5.8 (pp. 17-19), Tables 3-4 (pp. 16, 18). Official 3D-grounding cookbook: https://github.com/QwenLM/Qwen3-VL/blob/main/cookbooks/3d_grounding.ipynb (raw: https://raw.githubusercontent.com/QwenLM/Qwen3-VL/main/cookbooks/3d_grounding.ipynb) and its camera file https://raw.githubusercontent.com/QwenLM/Qwen3-VL/main/cookbooks/assets/spatial_understanding/cam_infos.json. **Read on**: 2026-10-24. The report gives very little on 3D grounding (one paragraph of data, one of evaluation, one prompt template). Most of the format facts below come from the official cookbook, not the paper.

## TL;DR
Qwen3-VL (dense 2B/4B/8B/32B, MoE 30B-A3B/235B-A22B) pretrains on a dedicated single-image 3D-grounding set: a referring expression in, a 9-DoF box `bbox_3d` out as JSON. The data are unified "following Omni3D" into "a virtual camera coordinate system". The cookbook defines the output as `[x_center, y_center, z_center, x_size, y_size, z_size, roll, pitch, yaw]`, with the centre "in camera coordinates (meters)", and projects it with an OpenCV pinhole model (x right, y down, z forward), which matches our frame. Our zero-shot prompt does deviate from the native template: it adds text intrinsics and a frame sentence, which Qwen3-VL was apparently never trained to read, and it asks for all objects in one query.

## Setup / method (relevant parts only)
- **Architecture**: SigLIP2 ViT. The 2B and 4B use SigLIP2-Large (300M), the larger ones SO-400M. A 2-layer MLP merger compresses 2×2 patches into one token. DeepStack injects multi-level ViT features into early LLM layers. Interleaved MRoPE. Pretraining runs in 4 phases (merger warm-up, then 8K/32K/256K context). Post-training is SFT, then strong-to-weak distillation (the small models are distilled from larger teachers), then RL that includes "visual grounding" tasks with rule-verifiable rewards.
- **2D grounding (§3.2.4)**: boxes and points use "a normalized coordinate system scaled to the range [0,1000]" (Qwen2.5-VL used absolute pixels). The point format is `{"point_2d": [x, y], "label": ...}` (App. B.6).
- **Spatial understanding data (§3.2.5)**: relational, affordance and action-planning QA. Quote: "all spatial references are expressed relative to other objects or scene frames, rather than absolute coordinates." So the only metric-coordinate supervision is the 3D-grounding set.
- **3D-grounding data (§3.2.5)**: "public collections of diverse indoor and outdoor scenes", reformulated as VQA. Each sample is "a single-view camera image", a referring expression, and "9-DoF 3D bounding box annotations in a structured JSON format". Because the sources "exhibit varying camera intrinsic parameters and inherent noise", they "filter out heavily occluded and inaccurate labels and follow Omni3D ... to unify all data into a virtual camera coordinate system". The datasets are not named, and the size of the set is not given. The referring expressions include synthesised detailed captions (attributes, layout, affordances). No physics or dynamics data is mentioned anywhere.
- **Native 3D prompt (App. B.5, used for ARKitScenes/Hypersim/SUN RGB-D eval)**: `<image> Locate the {class_name} in the provided image and output their positions and dimensions using 3D bounding boxes. The results must be in the JSON format: [{"bbox_3d":[x_center, y_center, z_center, x_size, y_size, z_size, roll, pitch, yaw],"label":"category"}]`. It is **one class per query, with no intrinsics and no frame description in the text**.
- **Cookbook format spec (verbatim)**: "x_center, y_center, z_center: Object center in camera coordinates (meters)". "x_size, y_size, z_size: Object dimensions (meters)". "roll, pitch, yaw: Rotation angles (radians)". Cookbook prompt: "Find all cars in this image. For each car, provide its 3D bounding box. The output format required is JSON: ...".
- **Cookbook camera handling**: per-image intrinsics from `cam_infos.json` are used **only for drawing**, via `x_2d = fx*(X/Z)+cx`, `y_2d = fy*(Y/Z)+cy`. That is the OpenCV frame (+x right, +y down, +z forward). If intrinsics are unknown, the fallback `generate_camera_params(fov=60)` builds K from a 60° FoV. The demo images have horizontal FoV of roughly 52-69° (my computation from cam_infos.json: 65.6, 51.9, 69.2, 61.1°).
- **Cookbook angle inconsistency**: the drawing code unpacks `x, y, z, x_size, y_size, z_size, pitch, yaw, roll`, which is not the documented roll, pitch, yaw order. It also multiplies the angles by 180 and then converts degrees to radians, so the angles are effectively in units of π. Sizes are applied as ±size/2 along the object's local x/y/z.
- **Omni3D convention (2207.10660)**: camera origin, "+x facing right, +y facing down, +z inward", centroid "in camera space meters". Cube R-CNN additionally predicts a *virtual depth* z_v = z·(f_v/f)·(H/H_v) with f_v = H_v = 512, which makes depth invariant to the intrinsics. The Qwen report does not say whether "virtual camera coordinate system" means only the unified axes or also this depth rescaling.

## Key results
- 3D grounding, mAP@0.15 on the Omni3D test sets (detection confidence fixed at 1.0; Tables 3-4):
  - **Qwen3-VL-2B Instruct**: ARKitScenes 56.2, Hypersim 12.0, SUN RGB-D 33.8. 2B Thinking: 47.7 / 11.2 / 28.6.
  - 4B Instruct 56.6 / 12.2 / 34.7. 8B Instruct 56.8 / 12.7 / 36.2. 32B Instruct 55.6 / 14.0 / 37.0.
  - Almost flat with scale: the 2B is about as good as the 32B at 3D grounding. Instruct beats Thinking at every size.
  - Flagship 235B-Thinking beats Gemini-2.5-Pro by 5.2 points on SUN RGB-D (§5.5). The per-dataset numbers for the flagship are in Table 2, which I did not transcribe.
- Embodied/spatial, 2B Instruct (Table 4): ERQA 28.3, VSI-Bench 53.9, EmbSpatialBench 69.2, RefSpatialBench 30.3, RoboSpatialHome 49.1. RefCOCO-avg 85.6, CountBench 88.4.
- mAP@0.15 is a very loose IoU threshold, so it says little about centre error in metres. No metric centre-error number is reported anywhere.

## Relevance to us
- **exp001_zeroshot_qwen3d, format check (our `prompts.py:48-53` + `parse.py:34-36`)**:
  1. **Field order and centre: no mismatch.** Our template copies the native field list verbatim, and `parse.py` takes `v[:3]`, which is the documented `x_center, y_center, z_center`. Size and rotation order do not matter because we never score them. The rotation convention is ambiguous even in Qwen's own code (above), so we should never start scoring sizes or angles.
  2. **Frame and units: no mismatch.** Omni3D, the cookbook projection, our `FRAME` sentence and our GT (`geometry.world_to_cam`, OpenCV cam2world) all use +x right, +y down, +z forward, in metres. A sign flip is therefore not the expected cause of the ~0.7 m smoke-test error.
  3. **Prompt deviates from native (a real mismatch).** We add (a) "A camera looks at objects on a table", (b) text intrinsics `fx, fy, cx, cy`, (c) the frame sentence, and (d) a list of several objects with a `"<object>"` label placeholder. Native prompts have none of (a)-(c) and ask for one class per query (B.5) or "all X" (cookbook). Nothing in the report suggests that the 3D data put intrinsics in the text: the varying intrinsics were handled by canonicalising into a virtual camera. So (b) and (c) are at best ignored and may push the 2B off-distribution. exp001 therefore measures "Qwen3-VL with our prompt", not strictly "native zero-shot". That should be stated in the report, or tested (IDEA-023).
  4. **A possible depth-scale bias of about 7%.** If "virtual camera" means Cube R-CNN virtual depth (f_v/H_v = 1, about 53° vertical FoV), Qwen's z is in the virtual camera's units. For our camera (448×448, fovy 50°, so fy ≈ 480.4, f/H ≈ 1.072), metric z ≈ 1.072·z_pred. At 0.9-1.3 m this is about 0.06-0.09 m. That is real for Task A but far too small to explain ~0.7 m, so the smoke-test error is mostly domain gap, not convention. IDEA-024 checks for a constant scale directly.
  5. **Domain gap.** The 3D training data are indoor and outdoor scenes graded on room-scale benchmarks (ARKitScenes, Hypersim, SUN RGB-D). Our objects are 5-12 cm synthetic primitives at about 1 m on a plain table. Weak zero-shot Task A is the expected outcome, and a strong positive image-dependence gap is not guaranteed.
  6. **Missing objects.** Asking for all objects in one query differs from per-class queries. Omission or duplicate labels (missing_rate) is a plausible harness failure mode, so the spec's validity criterion (missing_rate ≤ 5%) is well placed.
- **Task B**: the report mentions no dynamics or physics training data. Any zero-shot Task B skill must come from language priors over the action text, which fits exp001's hypothesis (B) that Task B is worse than static.
- **Why `center` gives [0,0,0]**: the only metric-coordinate supervision is in the `bbox_3d` JSON format (§3.2.5 says spatial-QA data avoid absolute coordinates). This is consistent with the smoke-test observation.
- **IDEA-014 ((u, v, depth) output)**: confirms that 2D points are native, as `point_2d` on a [0, 1000] normalised grid, not pixels. If IDEA-014 is run, targets should use the 0-1000 grid.
- **IDEA-019 (K-varying crops)**: the report indicates that intrinsics are canonicalised away rather than read from the prompt. A pretrained prior for using text K is therefore unlikely, and SFT would have to learn it. This supports 019 as a test of whether K can be learned at all.
- **Image resolution**: 448×448 should map cleanly onto the 32-px merged-token grid. I did not verify Qwen3-VL's patch size from the report text. This matters only for pixel-space diagnostics (IDEA-024, IDEA-014).

## Ideas for us
- **IDEA-023 Verbatim native 3D-grounding prompt for zero-shot (exp001 variant)**: replace the qwen3d prompt with the App. B.5 template, one query per object (`Locate the {name} in the provided image and output their positions and dimensions using 3D bounding boxes. The results must be in the JSON format: [...]`), with no intrinsics, no frame sentence, and the Task B action line kept for B. Single change: the prompt text. Expected: if Task A val_id error falls clearly, our additions were hurting the zero-shot readout and exp001's conclusion should use this prompt. If it does not change, the prompt is not the bottleneck. Cost: worktree prompt option, about 0.3 GPU h eval (N objects × queries).
- **IDEA-024 Frame/scale audit of zero-shot Task A predictions (CPU analysis of exp001 preds)**: on val_id Task A, (i) project the predicted and GT centres with K and report the pixel error separately from the z (depth) error, and (ii) fit a single global scale s minimising ‖z_gt − s·z_pred‖ (and per-axis sign/scale) and report the error after correction. Expected: s ≈ 1.07 with a large drop in error would indicate a virtual-camera depth convention (fixable post hoc). A small pixel error with a large z error would point to metric-depth failure (which motivates IDEA-014/015). A large pixel error would mean poor 2D grounding of small primitives (which motivates IDEA-004). Cost: about 0.5 day, no GPU, uses exp001's existing outputs.

## Caveats / disagreements
- The report never states units, frame or the virtual-camera definition. "Camera coordinates (meters)" comes from the cookbook, which is the vendor's usage documentation, not the paper. The virtual-depth interpretation is my inference from the Omni3D citation and is unverified.
- The 3D-grounding pretraining sources and the size of the set are not disclosed. Only the evaluation sets (ARKitScenes, Hypersim, SUN RGB-D) are named. I could not verify whether tabletop-scale objects (e.g. Objectron, which is in Omni3D) were included.
- All numbers are box detection mAP at IoU 0.15. They do not translate to our centre error in metres.
- The small models are distilled from larger teachers. Their 3D behaviour may reflect teacher outputs, not the 3D data directly.
