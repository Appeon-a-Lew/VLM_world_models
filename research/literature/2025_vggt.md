## TL;DR
VGGT is a ~1.2B feed-forward transformer that predicts camera parameters, depth, point maps and track features from 1 to hundreds of images in one pass (0.04 s and 1.9 GB for one frame on an H100). It supports a single image but the paper gives only qualitative single-view results and its scale is learned in a normalised, not metric, space.

## Setup / method
- Input: N RGB images (N=1 allowed; global attention then reduces to frame-wise). Output per image: camera (9 values: quaternion, translation, FoV), depth, point map, tracking features, aleatoric uncertainty.
- Architecture: DINOv2 patch tokens, 24 alternating frame-wise/global self-attention blocks, camera token + 4 register tokens per frame (first frame has distinct tokens = reference), camera head (4 self-attn layers + linear), DPT dense head over blocks 4/11/17/23. Tracking via CoTracker2 head.
- Conventions: **first camera is the world frame (identity extrinsics)**; principal point assumed at the image centre; point maps are in the first camera's frame (so for one image, camera frame, which is our target frame).
- Supervision: multi-task (camera, depth, point map, track) with GT; data mix incl. Co3Dv2, BlendMVS, DL3DV, MegaDepth, Kubric, ScanNet, HyperSim, Mapillary, Habitat, Replica, PointOdyssey, Virtual KITTI and a synthetic artist-asset set. GT normalised by mean point distance to origin; the net learns this scale (no metric rescaling). 160k iters, 64 A100 for ~9 days, max side 518.

## Key results (multi-view; baselines in brackets)
- Camera AUC@30 Re10K (unseen) 85.3 (MASt3R 76.4, DUSt3R 67.7), CO3Dv2 88.2 (81.8 / 76.7); ~0.2 s; with BA 93.5 / 91.8.
- DTU overall Chamfer 0.382 without GT cameras (DUSt3R 1.741; MASt3R with GT cams 0.374).
- ETH3D point map overall 0.677 depth+camera, 0.709 point head (MASt3R 0.826, DUSt3R 1.005).
- Ablations (ETH3D overall): alternating attention 0.709 vs global-only 0.827 vs cross-attn 1.061; dropping camera loss 0.834, depth loss 0.727, track loss 0.790 (multi-task helps).
- Features as a backbone: CoTracker + VGGT features TAP-Vid Kinetics AJ 57.2 (49.6); NVS on GSO without input cameras 30.41 PSNR (LVSM with known cameras 31.71).
- Runtime: 1 frame 0.04 s / 1.88 GB; 10 frames 0.14 s / 3.63 GB.
- **Single frame: supported but "not explicitly trained"; only qualitative figures, no quantitative single-view depth or point-map error in the part I read.**
- Limitations: no fisheye/panorama, degrades under extreme input rotation, fails on substantial non-rigid motion.

## Relevance to us
- It is the geometry encoder inside SpaceMind (IDEA-021/022). Before using it for IDEA-022, the key unknown is single-image quality at **12-25 deg elevation on 5-12 cm primitives at ~1 m on a plain tabletop**. The paper does not measure single-view accuracy, viewpoint extremes or metric scale; the "extreme rotation" limitation is a warning for exactly our val_ood_config.
- Scale: GT is normalised per scene and the net learns that scale, so single-image outputs are not guaranteed metric. For a Task A (metres) lookup we must fit or calibrate scale, e.g. using the known table or object sizes, and report scale bias separately (as in IDEA-042).
- Camera head gives FoV and camera pose relative to the first frame; for one frame this is identity, so camera *elevation* has to come from a table-plane fit in the point map, not from the pose output. That is an RGB-only route to a camera-pose text input (IDEA-016) without GT pose.
- Not relevant to Task B dynamics directly; its tracking head is for observed videos, and we have one frame.
- Tied to the image-dependence concern: a frozen geometry-first model is fully image-derived, so a VGGT-lookup baseline for Task A is an image-only perception floor with no text prior.

## Ideas for us
- **IDEA-045 (eval-only, no training): VGGT single-image point-map Task A baseline per split.** Run VGGT on each val RGB (single frame), take the point map at the GT 2D object mask, median xyz, apply one global per-split-free scale factor fitted on train episodes (so no per-split tuning), add the half-extent offset as in IDEA-015/042; report Task A error on val_id, val_ood_*, diag_elev/count/corner next to exp000/exp005 and the DA-V2 arm of IDEA-042. Expected: shows whether a frozen geometry model degrades at low elevation like exp000 (0.136 vs 0.016-0.024). Cost ~0.5 day, ~0.2 GPU-h; 1.2B params fits in 16 GB; install/availability unverified.
- **IDEA-046 (eval-only): can RGB-only geometry recover camera elevation?** Fit the table plane to the VGGT point map of each val image, derive camera elevation from the plane normal vs the optical axis, and compare with GT elevation per split (including 12-25 deg). Expected: if error is small (a few degrees) a predicted-elevation text input (IDEA-016 at test time without GT pose) is feasible; if it breaks at low elevation, IDEA-016 can only be an oracle diagnostic. Cost ~0.3 day, ~0.1 GPU-h.

## Caveats / disagreements
- Multi-view, real-world, static scenes with large baselines; ours is a single synthetic render with a clean textureless table. Domain gap unmeasured.
- 1.2B encoder is about 0.6x the size of our whole 2B VLM; adding it as a frozen feature branch (SpaceMind) is a memory/time cost; as an offline baseline it is cheap.
