## TL;DR
SR-3D adds a sinusoidal+MLP encoding of a per-pixel 3D position map to the 2D vision tokens, so one model handles single-view images (position map from Depth Anything V2 relative depth) and multi-view video (GT or MASt3R/CUT3R point maps). It beats prior region-VLMs on region QA, BLINK depth and VSI-Bench, but has no single-view GT-vs-predicted-depth ablation and no dynamics.

## Setup / method
- Input: image (or 32 frames) plus region prompts (box/mask/3D). Output: text answers (classification, QA, captions, metric measurements). No coordinate regression output.
- Single-view 3D PE: relative depth from Depth Anything V2 is back-projected to a camera-coordinate position map, then "canonicalized into a normalized world frame" so it does not depend on camera pose (the digest says no intrinsics values or normalisation formula are given). Encoded with sinusoidal features then a learnable point-wise MLP, resized to token resolution and **added** to the vision tokens (same family as IDEA-013).
- Multi-view: training uses GT depth, back-projected and moved by camera poses into one shared space, normalised; inference can swap in MASt3R/CUT3R pointmaps.
- Backbone: Section 3.3 says NVILA-Lite-8B (vision encoder frozen; 3D PE, projectors and LLM fine-tuned). Appendix E reportedly describes PaliGemma vision + Qwen-2-7B. The paper does not reconcile these (flag if we cite the backbone). LR 5e-5, cosine.
- Supervision: Stage 1 2D (~7M samples, NVILA instruction + region data; the appendix reportedly contradicts the main text on whether spatial data were excluded). Stage 2 3D: ScanQA, SQA3D, Scan2Cap, EmbodiedScan region/spatial QA, with box-from-mask and random frame-drop augmentation.
- Dynamic tiling (448x448 tiles of image and point map), tile-then-stitch region features.

## Key results (from digest; baselines in brackets)
- 2D benchmarks vs NVILA-Lite-8B: BLINK 83.9 (79.7), EmbSpatial 72.5 (68.9), RealWorldQA 68.1 (65.6), SAT 64.0 (62.6). Small +/- on others (GQA 64.2 vs 65.3, TextVQA 77.3 vs 78.1).
- COCO region classification mAP 78.0 / acc 88.6 (SpatialRGPT 72.9 / 82.9). BLINK Depth 90.3 (SpatialRGPT 87.9).
- SR-3D-Bench: qualitative avg 79.5, quantitative avg 83.3 (best region baseline GPT-4o+SoM 44.1 / 46.7). Zero-shot 2D-only model: Distance 68.5 vs base 6.6.
- 3D QA: ScanQA CIDEr 109.3 (Video-3D LLM 102.1), SQA3D EM 62.2 (58.6), Scan2Cap CIDEr 97.9 (83.8).
- VSI-Bench: abs. distance 52.8 (Gemini-1.5 Pro 30.9), object size 75.5 (64.1), room size 41.9 (below Gemini-1.5 Flash 54.4).
- Ablation (low confidence): without 3D PE and 3D pretraining vs full, ScanQA CIDEr 101.3 to 109.3, SQA3D EM 58.6 to 62.2; "3D PE without scaling gives only marginal gain". Multi-view GT vs CUT3R point clouds: ScanQA CIDEr 109.3 for both, i.e. predicted geometry is nearly as good as GT *in multi-view indoor scans*.
- Limitations stated: weak on orientation, static scenes only, single-view and multi-view are separate checkpoints.

## Relevance to us
- It is the clearest published recipe for IDEA-013/020 in a single-view setting: depth-derived xyz map, sinusoidal+MLP, added to tokens, LoRA/full fine-tune. That makes IDEA-013 a low-novelty, well-precedented change rather than a gamble.
- The "canonicalize so it does not depend on camera pose" step is directly on-topic for val_ood_config (elevation 12-25 deg vs train 30-60, a pose shift): the PE is intended to be pose-invariant. We output camera-frame centres, so a canonical-frame PE leaves the model to learn the frame change, which is itself an interesting contrast to a camera-frame PE (new idea).
- Evidence is all for static spatial QA (text answers, relative/metric distances). Nothing speaks to Task B (1 s dynamics) or to the image-dependence gap; any benefit would show up in Task A first.
- Its depth source is relative depth (DA-V2), so scale is lost; consistent with my DA-V2 note (IDEA-042). Our GT depth is the oracle upper bound; no evidence here on how much oracle vs estimated depth differs for single view.
- The "predicted ~ GT" multi-view result is weak support for expecting an estimated-depth arm to track the oracle, but it is ScanNet-style indoor data, not tabletop at 12-25 deg.

## Ideas for us
- **IDEA-044 (PE frame ablation, conditional on IDEA-013 being implemented)**: with the IDEA-013 xyz-PE, change only the frame the PE is expressed in: camera-frame xyz (baseline of IDEA-013) vs table-canonical xyz (origin on table plane, z up, from GT camera pose), keeping the output in camera frame. Expected effect: if the val_ood_config failure is an elevation/pose-dependence problem, canonical PE should help Task A there and may hurt Task B id slightly; if both equal, the PE content (not frame) is what matters. Cost: ~1.4 GPU-h for the second arm, plus a small transform in the data pipeline; no extra cost if IDEA-013 is run anyway.

## Caveats / disagreements
- Text-answer region VLM at 8B, not coordinate regression at 2B; our target is an exact camera-frame metric centre.
- Backbone and data-description inconsistencies inside the paper (see above).
- No single-view GT-vs-estimated depth ablation, no viewpoint-shift test, no dynamics, no blind/no-image control.
- Digest-based reading: exact normalisation and numbers should be checked against the PDF before being cited in a report.
