# OneCanvas: 3D Scene Understanding via Panoramic Reprojection

**Citation**: Bartłomiej Baranowski, Dave Zhenyu Chen, Matthias Nießner. NeurIPS 2026 (Spotlight), arXiv:2606.19253 (v1 17 Jun 2026, v2 27 Sep 2026). https://arxiv.org/abs/2606.19253, HTML: https://arxiv.org/html/2606.19253v2
**Read on**: 2026-10-24. I read the full HTML (method, results, ablations and the appendix on compute and task formats). The page does not include a depth-noise sweep or a single-view ablation, so those are absent here.

## TL;DR
Frozen Qwen3-VL ViT patch features from all views are lifted to 3D with metric depth, intrinsics and pose, then re-laid on a single equirectangular "canvas" around a chosen origin. The canvas positions drive the native M-RoPE axes (θ, φ, frame index), and a gated sinusoidal embedding of each patch's metric xyz is added to its feature. With LoRA and a synthetic spatial curriculum, this gives state-of-the-art SQA3D and VSI-Bench results at about 259 A100-equivalent GPU-hours.

## Setup / method
- **Input**: K = 32 RGB frames, each with metric depth D_k and camera-to-world pose T_k (OpenCV convention), plus a question. Training runs at 320×240; evaluation at 320×240 (SQA3D) and 640×480 (VSI-Bench, SPBench).
- **Unprojection**: the depth at the patch location is used with intrinsics rescaled to the feature-grid resolution, then T_k maps the point to world coordinates. Each patch stays a separate token: no rasterisation, no fusion of overlapping patches, no visibility test. Unobserved directions simply contribute no tokens.
- **Canvas placement**: q = Rᵀ(p − c), θ = atan2(q_x, q_z), φ = arctan(−q_y / √(q_x² + q_z²)). M-RoPE axes are set to W = θ, H = φ, T = frame index, each rescaled to [0, 100]. The RoPE itself is unchanged.
- **3D position embedding of q (canvas frame, metres)**: 136 channels, made of per-axis {sin, cos, raw} at 16 log-spaced frequencies in [0.1, 100] rad/m (99 ch), radial terms ‖q‖ and r_xz at 8 frequencies in [0.1, 10] rad/m (34 ch), and the unit ray q/‖q‖ (3 ch). A 2-layer MLP (hidden 64) maps these to the feature dimension, and the result is added through a learned scalar gate. In stage 1 the PE norm is pinned to half the mean visual-feature norm. The PE learning rate is 50× the base rate.
- **Model / training**: Qwen3-VL-8B with LoRA on the LLM attention and MLP layers. The ViT and token embeddings stay frozen, and there are no auxiliary losses. Stage 1 is a synthetic curriculum: boxes filled with real ViT patch features are placed at chosen 3D positions on empty canvases, objects are referred to by an inline patch copy rather than a class name, and the answer distributions are controlled to avoid shortcuts. It uses LoRA r = 256 with randomised canvas centre and yaw. Stage 2 trains a new LoRA (r = 64, 10k steps) on VSI-Bench-style data, SQA3D and ViCA. The total is about 518 raw GPU-hours on A6000s.
- **Supervision**: next-token cross-entropy on text answers. Metric answers are written as text, e.g. distances "rounded to one decimal" and 3D box readouts as centre + extents.

## Key results
- **SQA3D** EM@1: 65.3 vs Ross3D 63.0. VSI-Bench avg: 71.3 vs SpaceMind 69.6. SPBench (zero-shot, OOD): 72.1 vs SpaceMind 67.3.
- **Predicted geometry** (Depth Anything 3 at inference only, no retraining): 65.3 → 64.9 (SQA3D), 71.3 → 70.0 (VSI), 72.1 → 71.3 (SPBench). Swapping in an estimator costs little.
- **Ablations (VSI-Bench)**: full 71.3; without 3D PE 70.4 (Abs. Dist. 62.3 → 58.1, Room Size 76.8 → 71.3, Rel. Dist. 73.1 → 70.3, but Route 60.8 → 66.0); panorama + PE without curriculum 68.5; panorama only 65.3; base VLM with plain multi-view input 65.5.
  - The metric PE mainly helps metric questions (absolute distance, size). The curriculum carries much of the gain.
- **Canvas origin (SQA3D)**: agent pose 65.3, random camera 61.4, scene centre 61.2, outside scene 59.8. A reference frame matching the question's frame helps most on the viewpoint-dependent "Which" questions.
- **Continuous vs rasterised canvas (VSI)**: 71.1 vs 68.2 / 67.7 / 65.8 at decreasing raster resolution. Feature canvas vs rendered RGB panorama (matched 2k steps): 60.8 vs 52.1.
- **Seam failure**: when the longitude seam falls between two objects 15° apart, distance error goes 0.14 m → 1.23 m.
- **Seeds (3)**: VSI 70.4 ± 0.6, SQA3D 65.1 ± 0.9.

## Relevance to us
- **The val_ood_config failure (Task A 0.016 → 0.136 m; Task B worse than static).** `sim_ood_config.yaml` lowers camera elevation to 12–25° (train 30–60°) and also changes object count (4–5 vs 1–3) and placement (a corner cluster). Our camera-frame target depends on the unknown camera pose. Because fx, fy, cx, cy are constant across all episodes, the intrinsics line in our prompt carries no information, and the model must have learned an implicit pixel→metric map tied to the training elevation range. OneCanvas skips that inference: each visual token carries its own metric xyz, so reading out a centre becomes "find the object's tokens, copy or average their coordinates", which should not depend on elevation.
- **For a single view the canvas reduces to something simple.** With one camera and the canvas centred at the camera with R = I, (θ, φ) is just a monotone remap of pixel position. OneCanvas then amounts to "normal image tokens + a gated MLP embedding of each patch's camera-frame xyz from depth". We already store `depth_t0.npz` and K, and our targets are already in the camera frame, so q equals the target frame exactly. No pose is needed.
- **Task A vs B**: the PE gives Task A an almost direct readout, since patch xyz sits on the object's visible surface rather than its centre. That separates perception from dynamics, so a remaining Task B error on val_ood_config would be a dynamics error. That matches the decomposition we want, and it complements IDEA-002 (delta prediction).
- **Image dependence**: if xyz is injected, the "none/blank/swap" ablations must also remove or swap the depth/PE, otherwise the gap is ill-defined. A model that reads only the PE and ignores RGB would still be "image-dependent" in the geometric sense, which is fine, but the reporting needs care.
- **Their evidence on depth source** (GT vs Depth Anything 3 costs about 0.4–1.3 points) suggests a GT-depth result would not be a pure oracle artefact. Still, we should report a predicted-depth variant before claiming RGB-only generalisation.

## Ideas for us
- **IDEA-013: per-patch camera-frame xyz embedding (OneCanvas-style, single view).** Unproject each merged vision token's pixel block (median depth, K) to camera-frame xyz. Encode it with the OneCanvas 136-ch sinusoid recipe, pass it through a 2-layer MLP, and add it via a zero-initialised scalar gate to the visual tokens after the merger. Train the MLP (higher LR) plus the existing LoRA. Expected: a large drop in Task A error on val_ood_config (toward the ID level of ~0.02 m) and Task B at or below static there. Cost: about 1–2 days of model surgery plus about 1.5 GPU h. The image ablations must also blank the PE.
- **IDEA-014: (u, v, depth) answer format with analytic unprojection.** The model outputs pixel coordinates (Qwen's native 0–1000 grid) plus the centre depth z, and we unproject with K to camera xyz for scoring. 2D pointing is viewpoint-agnostic in form and native to Qwen3-VL, so only z has to be inferred. Expected: lower Task A error on val_ood_config, and a decomposition of the error into the 2D part and the depth part. Cost: prompt/target and eval change plus 1 SFT run (about 1.4 GPU h).
- **IDEA-015: depth-lookup oracle for Task A (diagnostic upper bound).** Same as IDEA-014, but z comes from `depth_t0` at the predicted (u, v), offset to the centre along the ray using the object's half-extent. This is eval-only on top of IDEA-014 outputs. Expected: shows whether the val_ood_config failure is in 2D localisation or in depth/metric inference. Cost: about 0.5 day, no GPU training.
- **IDEA-016: camera pose as text (the cheapest "give the model the geometry").** Add `camera elevation E deg, distance D m above/from the table centre` (or the table-plane normal and offset in the camera frame, derived from `cam2world`) to the prompt. Expected: some reduction of Task A error on val_ood_config if the model learns to condition on it. However, the 12–25° values are numerically outside training, so extrapolation in text may fail. That would itself be informative when compared with IDEA-013, which supplies per-token geometry. Cost: prompt change plus 1 SFT run (about 1.4 GPU h).

## Caveats / disagreements
- OneCanvas is multi-view, indoor, and uses an 8B model with r = 256 LoRA and about 500 GPU-hours. We have one view, a 2B model and small budgets. Single-view benefit is not ablated in the paper.
- Their metric gains from the PE are modest (+0.9 VSI avg). Most of the gain comes from the canvas plus curriculum. In our single-view case the "canvas" part is a no-op, so the PE alone has to carry the effect.
- Patch xyz is on the visible surface, not the object centre, so the model still needs to learn the surface→centre offset (shape and size dependent). That interacts with val_ood_objects (new shapes).
- The paper does not evaluate camera-elevation shifts. Its viewpoint evidence is only the canvas-origin ablation and yaw randomisation during training, so it does not directly test our failure.
- Some numbers on the HTML page are inconsistent (71.1 vs 71.3 for the same continuous-canvas setting). I quoted both.
